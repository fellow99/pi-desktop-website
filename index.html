Open source · MIT · Unofficial Pi desktop shells

The Pi agent harness, at home on the desktop.

Pi Desktop runs the upstream Pi Web UI — untouched — inside native shells for Windows, macOS, Linux, HarmonyOS and Android. The Pi host and its Next.js server run inside the app itself, and the window loads that UI from the same origin: no cloud relay, no CORS, no login page, and no pi binary needed on your PATH. Your existing sessions, credentials and extensions come along.

$ why a native shell

Why a native shell

The whole Pi experience — none of the browser tab.

100% upstream Pi & Pi Web — the SDK and UI run unmodified.

The Pi SDK and the Pi Web UI run unmodified; the shell only assembles them. The desktop shell ships zero patches, so upstream improvements land without a fork to rebase. The Electron on HarmonyOS Edition carries 2 registered patches, the HarmonyOS Edition applies its 6 pi-web patches and the Android Edition a parallel set of 6, all as idempotent, reversible files at build time — every upstream working tree stays pristine.

Local-first, in-process.

The Pi host and its Next.js server run inside the app's own main process — no sidecar, no orphaned Node processes — and the UI loads from that same origin. Nothing is relayed through the cloud, and there is no login page to paste a password into.

A desktop citizen.

System tray, native notifications driven by tailing the session log, single-instance focus, a remembered window size and position, and external links handed to your system browser.

Shares your pi CLI environment.

Defaults to ~/.pi/agent, so sessions, credentials, extensions and MCP configuration are the same ones your terminal already uses. Switch to an app-private directory in settings when you want isolation.

Pi Desktop

Electron · Windows · macOS · Linux
  • Electron 43.7.9 (Node 24.21.0 / Chromium 150): pi-web's Next.js server runs in the main process, not as a sidecar.
  • Random loopback port with a host-generated random password — credentials are injected, so the login page never appears.
  • Ships pi-dist.tar.gz, extracted into userData on first launch and skipped afterwards (SHA-256 marker).
  • Installers: Squirrel (Windows), DMG (macOS), deb / rpm / zip (Linux) — unsigned, so SmartScreen and Gatekeeper will ask.
  • Status: v0.15.0 · packaged end-to-end verified on Windows (smoke 10 + e2e 11 + probe 7, all PASS); macOS and Linux pending.

Pi Desktop · HarmonyOS Edition

ArkWeb + in-process Node · 2-in-1 / tablet / phone / TV
  • No Chromium and no Electron: an ArkTS host whose ArkWeb view loads the local pi-web server, which runs on a real Node.js runtime inside the app process (@fellow99/node-bridge: dlopen + node::Start).
  • Same in-process host and same origin as the Electron on HarmonyOS Edition — the difference is which runtime provides Node, and the payload is far smaller.
  • The runtime mode is fixed at build time to compat (--jitless): 2in1, tablet, phone and tv all behave the same — no per-device distinction.
  • No runtime switching, no setting for it. --jitless is a process-wide mode, an in-process Node starts once per process and a failed start is terminal — one wrong guess takes the whole app down. A jit variant means changing a build-time constant and rebuilding.
  • compat disables code-mode: the JS sandbox needs WebAssembly and cannot coexist with --jitless (its self-test fails, so the tool is never registered). Everything else is unaffected — chat with streaming, image attachments and vision, the Git extension, file and shell tools, and the ArkWeb page itself.
  • Verified on device — HUAWEI MateBook Pro (HAD-W24 / HAD-W32) and HUAWEI Enjoy 90 (JUY-AL80, phone), HarmonyOS API 26; capability parity is tracked feature by feature in docs/001-能力复刻评估.md.
  • Known limitations: no terminal / PTY (the platform has no devpts); the runtime mode is fixed to --jitless (compat), so there is no real-JIT ACL dependency and WebAssembly / code-mode is unavailable.
  • Status: v0.15.0 · built this round (signed HAP; boot/render/version/DeepSeek key/sandbox workspace/text chat/image chat verified on device). Historical: 0.12.x scaffold + Phase 1 capabilities on device.

Pi Desktop · Electron on HarmonyOS

Electron-on-HarmonyOS · 2-in-1 & tablet
  • Electron 37.2.3 / Node 22.17.0 on the harmonypc-electron runtime, packaged as a HAP.
  • Built, signed and verified on device — HUAWEI MateBook Pro (HAD-W32), HarmonyOS API 26.
  • The full upstream Pi Web UI; sessions persist inside the app sandbox.
  • Binds 0.0.0.0 and the window connects over the LAN IP, since HarmonyOS isolates loopback the other way.
  • Known limitations: no terminal / PTY, no git, no ripgrep or fd binaries, plugin installs are local-source only.
  • Status: v0.15.0 · versionCode 1500 · signed HAP built this round; on-device verification this round (boot / render / version badge / DeepSeek key / sandbox workspace / text chat / image-analysis chat).

Pi Desktop · Android

System WebView + in-process Node · phone / tablet
  • No Chromium and no Electron: a Kotlin host whose system WebView loads the local pi-web server, which runs on a real Node.js runtime inside the app process (aosp-node-bridge 0.2.0 + Maven Central node-runtime 26.13.0 small-ICU, dlopen of libnode.so).
  • Same in-process, same-origin model as the HarmonyOS Edition — the difference is the platform and the Node engine source.
  • Default JIT runtime (WASM probe passes); the jitless/ pure-JS layer installs only if WebAssembly is missing.
  • Real terminal shell is mksh (login sh -l). Five real cross-compiled CLIs ship on PATH: git、node、npm、pnpm、python、pip、uv (from aosp-*-cli, via .profile functions); system built-ins include toybox, awk/sed/tr, tar/gzip, sha256sum, curl, ping, pm, getprop, logcat. The pure-JS android-git (isomorphic-git) and in-process android-pnpm extensions were removed in 112 — git and pnpm now run as real binaries (no gcc/make, so no native node-gyp / pip sdist builds).
  • PTY terminal panel is now productized (node-pty 1.1.0, /api/terminal supported) alongside the plain shell.
  • Extensions ship in the payload: android-exec, android-search, android-pty, workspace-roots, SAF and more.
  • The only edition with a real foreground service for background keep-alive; 127.0.0.1 random port, loopback password-free, SAF directory picker.
  • Engine provenance is gated by verify-runtime.mjs against runtime.lock.json (SHA-256 + ELF gates); CI then runs zipalign -P 16 and the compliance gates.
  • Status: tag v0.15.0 builds a signed APK and publishes a GitHub Release (APK + .sha256); in-app version 0.15.0 / versionCode 1500.
View on GitHub

Together, the four editions cover Windows, Linux and macOS (Electron), HarmonyOS (where two independent editions ship: Electron on HarmonyOS keeping the Electron runtime and HarmonyOS using ArkWeb with an embedded Node runtime) and Android (system WebView with an embedded Node runtime). Four unofficial open-source shells built on Pi and Pi Web; the desktop shell is patch-free, the Electron on HarmonyOS Edition carries 2 registered patches, and the HarmonyOS and Android Editions each carry 6 idempotent patch files. Not affiliated with, or endorsed by, the Pi or Pi Web authors. The desktop installers are unsigned, so expect a SmartScreen prompt on Windows and Gatekeeper on macOS; the Android APK is self-signed.

$ how it works

One host. One origin. Zero friction.

  1. 1

    In-process host

    The shell starts pi-web's Next.js server inside the Electron main process.

  2. 2

    Same-origin UI

    The window loads http://127.0.0.1:<port>/ from that very server.

  3. 3

    Upstream data plane

    The standard Pi Web UI drives it: fetch('/api/*') up, SSE down.

No CORS · No custom protocol · No login page.
